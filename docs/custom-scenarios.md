# 基于编辑器的具体示例

关联：[编辑器](scenario-editor.md)、[DSL](scenario-schema.md)、[运行机制](runtime.md)、[个人存档](personal-saves.md)。本文件维护具体内容与制作步骤；创作功能和通用执行分别由所属规范维护。规则夹具与通过编辑器制作的示例产物分别管理。

## 1. 制作与交付规则

示例制作必须使用标准编辑器从空白创建两个世界，经保存重开、校验、试玩、定稿和导出完成。不能把既有夹具导入成功当作从空白制作证据，不能直接改库或手写导出 JSON 修补编辑器缺口。

创作域管理模板目录，示例只提供经编辑器验证的具体内容。有效示例可以进入只读模板目录，复制形成本人草稿；模板标识与 editor 自动生成的 metadata／实体／规则 id 分开。既有夹具供语义对照，具体 id 不要求与新编辑器产物相同。

交付含两份有效 ScenarioDefinition、作者操作说明和可复查证据。平台 draft／revision／release 的对应关系只放实施记录，导出的定义无平台身份／存档。标准导出和草稿交换规则以编辑器／API 为准，本文件不另建格式。

## 2. 栏目制作顺序

| 顺序 | 编辑器操作 | 检查 |
| --- | --- | --- |
| 1 | 空白创建；填写剧本资料、背景、回合尺度 | 保存为本人草稿，不使用模板导入替代本次制作 |
| 2 | 添加角色、阵营／地点、选玩家、添加关系与初始记忆 | 通过引用选择器绑定；分别配置公开与私有受众 |
| 3 | 添加状态 key、label、类型、范围、单位、初值 | 初值同步；控制者用实体候选，不能手写内部 id |
| 4 | 添加动作、参数、条件树与有序效果 | 使用已有控件，区分动作权限与结果受众 |
| 5 | 配置 NPC 顺序、候选与具体参数 | 候选只选有权限动作，不能用参数声明代替具体值 |
| 6 | 按说明配置事件、目标和叙事 | 顺序、重复标记、终局优先级明确 |
| 7 | 保存、重开、校验并修复定位问题 | 显式确认保存修订；没有 JSON 兜底编辑 |
| 8 | 独立试玩验证成功与失败 | 每路径新会话，记录回合与已结算变化 |
| 9 | 定稿、导出、从本人定稿进入正式游戏 | 产物取同一已保存定义，修改草稿不改既有局 |
| 10 | 正式保存、退出重登、恢复并继续 | 用世界域真实接口，原世界与检查点保留 |

无法表达的规则归引擎能力设计，无法操作的内容归编辑器能力设计；补齐所属规范与通用能力后重新制作。示例不增加题材专用执行代码。

## 3. 大明末年危局

这是机制验证用的游戏局势，数值不对应历史财政与兵力。时间展示为 1643 年起，每回合一周；使用虚构职位 NPC，避免把尚未考证的历史人物履历当作事实。

| 内容 | 首期设置 |
| --- | --- |
| 实体 | 玩家皇帝、财政官、前线将领；朝廷和敌对阵营；北京与前线地点 |
| 状态 | 国库 100、前线军饷 0、已用军费 0、赈济资金 0、军队忠诚 50、北京控制者为朝廷 |
| 数值范围 | 资金字段 0–1000，统一单位“财政点”；忠诚 0–100 |
| 初始记忆 | 军饷与赈济同时申请拨款；前线将领私有担忧，只对该角色可见 |
| 玩家动作 | 调拨军饷、拨款赈济、等待；拨款金额为 1–100 的整数参数 |
| NPC 行为 | 财政官优先候选为转移 10 点到赈济资金，要求国库充足且赈济资金低于 30；前线将领无固定候选 |
| 第一个事件：欠饷 | 军饷不足 10 且忠诚至少 5 时，忠诚减 5；可重复 |
| 第二个事件：支付 | 军饷至少 10 时，从军饷转移 10 到已用军费；可重复 |
| 第三个事件：失守 | 候选回合至少 8 且忠诚低于 40 时，北京控制者变为敌对阵营；不可重复 |
| 失败 | 北京失守，优先级 0 |
| 成功 | 第 12 回合后仍控制北京且忠诚至少 40，优先级 10 |

三个事件按上述顺序执行。欠饷检查在支付之前，避免支付后余额不足导致同回合被重复惩罚。已用军费表示支出累计，不把支出返还国库。

可达性设计：第一回合把 100 点全部拨给军饷，随后等待，能支付前 10 回合；第 11、12 回合忠诚分别降至 45、40，满足成功。一直等待且不拨军饷，则第 8 回合达到失守条件。内容调整后仍需按这些预期路径验证。

这是基础结算样例，不代表完整历史模拟或最终可玩性。赈济目标与更多角色利益可在后续内容迭代扩展。

编辑时角色、阵营和地点的内部 id 自动生成。controller 的初值、set 效果及 eq 条件从阵营选择器选择“朝廷／敌对阵营”，不把旧夹具的 id 字符串直接抄进文本框。军饷／赈济动作分别建立 amount 整数参数和 transfer，财政官候选无参数；事件按欠饷、支付、失守排序。

## 4. 空间站维修

| 内容 | 设置 |
| --- | --- |
| 世界与玩家 | 虚构受损空间站；指挥官为玩家，工程师为 NPC；每回合一小时 |
| 状态 | reserve=30、repair-energy=0、spent=0，均 0–100、单位能源点；integrity=0，范围 0–100、单位 % |
| 玩家动作 | 分配能源：amount 1–30，reserve 转移到 repair-energy；等待：无效果 |
| 工程师动作 | 条件：repair-energy≥10 且 integrity≤60；先转移 10 到 spent，再 integrity 增 40 |
| 演化 | 工程师一个候选“维修”，无参数；事件为空，记忆窗口为 3 |
| 目标 | integrity≥80 时成功、priority=0；候选回合≥4 时失败、priority=10 |
| 内容说明 | 单位与财政示例不同，全部规则仍用相同字段、条件和效果控件 |

成功路径：第一回合分配能源 20，工程师消耗 10 后完整度 40；第二回合等待，完整度 80 并成功。失败路径：独立会话一直等待，第 4 回合超时。没有阵营、地点或事件仍是合法空集合，应能只用相同编辑器控件完成。

## 5. 对照、证据和局限

两个题材的规则路径与编辑器制作流程分别验证。示例交付须覆盖从空白制作、重开、定稿、导出与实际运行，并检查玩家私有信息过滤及草稿／定稿／世界快照隔离；规则夹具不能替代编辑器制作。

内容数值为机制示例，不是完整历史或空间站模拟。局势、角色描述和具体字段值只有本文件一份设计来源；引擎不得按题材名分支。格式／执行能力变化时先调整引擎规范，编辑器同步控件，再重新制作受影响示例。
