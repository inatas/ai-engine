# 用户鉴权与个人存档

更新日期：2026-10-12。状态：设计依据，尚未实现。  
关联文档：[全局架构](architecture.md)、[剧本编辑器](scenario-editor.md)、[运行机制](runtime.md)、[应用接口契约](api-contract.md)。  
关联开发项：[首期实施 note](../note/001-world-engine-foundation.md)。

## 1. 用户、角色与权限

User 是平台账号；Character 是剧本中的角色；AuthSession 是登录会话；WorldSession 是一次游戏。四者不能混用标识或授权逻辑。

一次请求先确认登录身份及数据归属，再检查玩家控制的角色和游戏行动权限。拥有个人存档不等于能在玩家界面看到所有 NPC 的秘密。作者编辑自己剧本时允许看到完整定义，试玩调试与正式玩家响应仍分开。

首期所有草稿、定稿、试玩和个人存档均为私有。多人协作、分享授权与管理员代操作不在首期范围。

## 2. 鉴权方案

首期设计为本地账号体系：用户名与密码注册、登录、退出、查看当前用户。使用成熟库处理密码哈希与安全随机令牌，不自制密码算法。

密码只保存使用 Argon2id 等符合当前建议的密码哈希，不保存明文或可逆密文；具体库与参数在实施时核实并记录。依据：[OWASP 密码存储指南](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)。

密码输入不静默截断，登录失败统一提示账号或密码错误，登录请求限制重试频率；具体阈值作为部署配置并在实现 note 中记录。依据：[OWASP 鉴权指南](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)。

服务端保存 AuthSession，浏览器仅持有随机会话令牌，令牌不包含可自行编辑的 user_id。登录成功创建新令牌，退出或过期后服务端拒绝旧令牌。设置绝对有效期与空闲有效期，不仅依赖浏览器清理。令牌摘要可持久化，原始令牌不进入业务日志。

采用同源浏览器与 API，认证 Cookie 使用 HttpOnly、SameSite 及生产 HTTPS 下的 Secure。修改数据的请求还需防 CSRF 校验，不将 SameSite 当成唯一保障。会话生命周期与 Cookie 约束参考：[OWASP 会话管理指南](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)。

开发环境可以仅在回环地址运行；正式联网部署要求 HTTPS。首期暂不加入第三方登录、多因素认证与邮件找回，不能以固定演示账号或客户端 user_id 替代真正登录。

## 3. 服务端归属检查

草稿、定稿、WorldSession 和 SaveGame 均包含服务端建立的 owner_user_id。创建时取自已验证登录会话，更新时不可通过请求修改。

列表查询限定当前 owner_user_id。按 id 读取、修改、试玩、启动游戏、提交回合、保存和恢复也逐次检查归属；不能仅保护列表界面。其他用户的对象与不存在对象统一返回不可访问，内部日志可区分原因。依据：[OWASP 授权指南](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)。

读取某个 id 前先以当前用户范围查询；不把别人的内容返回后再由浏览器隐藏。请求中的 owner_user_id、用户目录或客户端角色 id 均不能成为可信身份来源。

公共示例模板由服务端提供，作为新草稿的复制来源；复制后的草稿由当前用户拥有，不开放其他用户私有定稿。

## 4. 数据与存储职责

首期使用 PostgreSQL + Prisma 事务保存账号、登录会话、剧本内容与个人游戏数据；数据访问仅位于服务端，详见[技术选型](technical-stack.md)。数据库是服务端数据，不要求玩家管理本地存档文件，不维护 SQLite 并存实现。

| 对象 | 关键数据 | 变化方式 |
| --- | --- | --- |
| User | user_id、规范化登录名、password_hash、创建时间 | 用户注册建立 |
| AuthSession | 登录会话 id、令牌摘要、user_id、有效期、撤销状态 | 登录建立，退出或过期失效 |
| ScenarioDraft | owner、document、revision、更新时间 | 保存草稿条件更新 |
| ScenarioRelease | owner、来源草稿与修订、完整定义快照 | 每次定稿新建，不原地覆盖 |
| WorldSession | owner、mode、schemaVersion、剧本快照、状态、历史、revision | 每个成功回合事务更新 |
| SaveGame | save_id、owner、名称、schemaVersion、来源会话及回合、完整世界检查点、创建时间 | 每次显式保存新建，不覆盖旧检查点 |

完整世界载荷保存为 PostgreSQL JSONB；账号归属、对象 id、revision、schemaVersion 与检索信息为独立列。约束与索引至少覆盖登录名唯一性、所有权查询和条件更新。Prisma 查询结果中的 JSON 仍需运行时校验，不能仅依赖 ORM 类型。

### 存档版本门禁

WorldSession 的世界载荷与 SaveGame 的检查点根部必填 schemaVersion，初始为 1，与存储版本列一致；服务端唯一当前版本常量决定可读取格式。创建、回合保存、检查点复制与恢复均由服务端写入，不接受客户端版本选择。

所有世界读取、继续、行动、保存与恢复，先验证归属，再检查版本，最后校验完整载荷、剧本引用及状态一致性。旧版本、未知版本、非法或缺失版本返回 checkpoint_version_unsupported；同版本损坏或列与载荷版本不一致返回 checkpoint_invalid。均不推进世界、不写检查点、不创建恢复会话。相关入口的去重结果也不能绕过当前版本门禁。

个人世界与检查点列表只读独立概要列，提供 schemaVersion 和 loadable；版本不支持时仍可显示本人名称与时间，标记不可继续或恢复。loadable 只表示版本支持，不代替详情读取时的完整校验。正式玩家界面不提供旧版转换入口。

格式或恢复语义发生破坏性变化时递增 schemaVersion；嵌入 DSL 或事件解释改变而使旧存档失效时同样递增。只读取当前版本，旧格式不补默认值、不迁移、不使用旧解释器。schemaVersion 是格式标识，revision 是并发修订，release_id 是定稿身份。

## 5. 保存的语义

成功回合自动持久化 WorldSession 的最新状态；用户点击“保存游戏”创建一个具名 SaveGame 检查点。自动保存保证继续游戏不会丢失已提交进展，手动检查点允许以后回到指定时刻。

手动保存由服务端读取本人 play 会话的已提交状态，并检查 expected_revision；不接收浏览器上传的权威世界状态或 owner。检查点包含剧本快照、字段值、回合、已触发事件、角色知识、终局和历史。

保存名称仅用于展示，不作为文件路径或身份标识。每次保存产生独立 save_id，允许同名；界面通过回合与时间区别。首期不要求覆盖、删除、改名或云端共享。

保存请求带 request_id，按用户与操作范围去重；重复确认不会创建多个检查点。修订冲突时提示当前进展已经变化，让用户刷新后重新保存，不静默保存与屏幕不同的回合。

## 6. 个人存档列表与读取

“我的存档”仅展示本人 SaveGame：名称、剧本名称、保存回合、时间、终局状态。分页查询同样附带归属过滤，不展示其他账号的数量或名称。

读取存档先检查归属、当前 schemaVersion 与完整结构，向浏览器返回玩家视角的概要。完整剧本快照、NPC 私有记忆和回合内部数据只在服务端恢复流程中使用。

用户可从退出前已自动持久化的本人 WorldSession 继续，也可选择手动 SaveGame 恢复；列表明确区分当前游戏与历史检查点。

## 7. 恢复及后续行动

恢复检查点时创建新的 WorldSession，赋予新的 session_id，owner 来自当前身份，mode 为 play。复制保存时的剧本、状态、回合、记忆与事件标记；检查点和原会话保持原样，避免读档操作悄悄覆盖新进展。

新会话的写入 revision 从 0 开始，请求去重账本为空。历史回合保留原始来源，但旧分支的请求标识不会阻止新分支继续行动；后续新请求的幂等范围是新的 session_id。

恢复不重播事件、不重新扣费，也不采用编辑器最新草稿。加载到同一回合应得到同样的世界状态；终局存档仍是终局，不能靠恢复绕过结束条件。

恢复请求也去重，重复确认返回已经创建的新会话。格式或规则语义调整后，旧数据不要求可读，不开发存档迁移。

## 8. 多标签页与提交

WorldSession 的变更要求 expected_revision；服务端按 owner、session_id 与 revision 条件提交整个新回合。两个标签页从同一状态行动时只允许一个成功，另一个返回冲突并重新加载。

一轮状态、历史、知识、事件标记、请求结果和 revision 在同一事务提交。保存检查点和恢复会话也使用事务；失败不报告成功，不留下半条存档或可见的部分世界状态。

检查点保存不改变来源会话的 revision。两个独立合法保存可各自产生检查点；相同请求重试才去重。保存与行动竞争时按事务中的最新 revision 判定，已提交的旧回合检查点仍合法，过期页面在世界推进后提交保存则拒绝。

revision 是写入一致性，不是旧版兼容。用户登录到多设备并不等同于多人共玩同一世界；首期仍为每局单玩家。

## 9. 应用操作约定

| 操作 | 认证与输入 | 返回／结果 |
| --- | --- | --- |
| 注册、登录 | 登录名与密码；防跨站与限流策略 | 用户概要；登录建立 Cookie |
| 当前用户、退出 | 有效 AuthSession；退出撤销服务端会话 | 用户概要或退出完成 |
| 草稿列表、创建、读取、保存 | 当前用户；保存含 expected_revision | 本人草稿与修订 |
| 校验、试玩、定稿 | 本人草稿或定义；绑定修订 | 定位问题、preview 会话或 release_id |
| 新游戏 | 本人 release_id、request_id | 新 play 会话及玩家视图 |
| 提交动作 | 本人 session_id、request_id、expected_revision、动作参数 | 已提交回合及新的修订 |
| 保存游戏 | 本人 session_id、expected_revision、名称、request_id | save_id 与保存概要 |
| 当前游戏／存档列表、详情 | 当前用户，查询始终限定本人 | 玩家可见概要 |
| 恢复存档 | 本人 save_id、request_id | 新 session_id 与恢复状态 |

HTTP 路径、输入字段、响应视图、错误与去重范围以[应用接口契约](api-contract.md)为准；所有操作必须遵守上述语义，不以浏览器缓存代替存档持久化。具体实现变更时同步回写，不另建兼容接口。

## 10. 验证要求

至少使用两个真实独立测试账号与未登录状态，直接请求读取、修改、保存、恢复与动作入口。改变对象 id、伪造 owner、Cookie 过期、退出后重用令牌、并发修订、请求重试与事务失败都要有验证记录。

这份文档给出设计约束，不能作为鉴权或存档已经可用的证据。实际功能按关联 note 完成并验收。
